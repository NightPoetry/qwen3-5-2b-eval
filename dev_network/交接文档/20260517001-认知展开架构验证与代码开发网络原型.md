## 一、项目概况

**定位**: 让 Qwen3.5-2B（极小模型）通过系统编排完成复杂代码开发任务。

**核心思想**: 2B 模型是单线程处理器——一次只能做一件简单的事。系统负责任务分解、状态管理、确定性操作；模型只在隔离上下文中回答简单问题。

**技术栈**: Python + Qwen3.5-2B（LM Studio, OpenAI 兼容 API）

**模型服务**:
- 2B: `http://localhost:1234/v1/chat/completions`，模型名 `qwen3.5-2b`
- 27B（备用）: `http://localhost:1234/v1/chat/completions`，模型名 `qwen3.6-27b`

## 三、架构总览

### 数据流

```
用户输入: "帮我做一个待办事项应用"
    │
    ▼
Phase 0: 交互设计（模型，隔离对话）
    输入: 用户需求
    输出: "点击添加→列表追加 / 点击删除→移除 / 点击完成→标记"
    │
    ▼
Phase 1: 元素提取（模型，隔离对话）
    输入: 交互描述
    输出: "input 输入文本 / button 添加 / ul 列表"
    │
    ▼
Phase 2: 接口契约生成（系统，确定性代码）
    输入: 元素列表
    操作: 关键词匹配 → 分配 ID → 生成事件绑定
    输出: {elements:[{id:"taskInput",...}], events:[...], data:{...}}
    │
    ▼
Phase 3: 分层代码生成（模型，每层独立隔离对话）
    HTML生成 ← 契约中的"ID+标签"
    CSS生成  ← 契约中的"元素类型+用途"
    JS生成   ← 契约中的"事件+数据流"
    注意: JS 不看 HTML，各层只看契约
    │
    ▼
Phase 4: 确定性验证修复（系统，纯代码）
    - viewport 缺失 → 自动添加
    - body嵌套在head → 自动修正结构
    - JS混入HTML → 提取<script>内容
    - CSS有markdown标记 → 移除
    │
    ▼
输出: output_todo_v3/{index.html, style.css, app.js}
```

### 核心架构决策

| 决策 | 原因 |
|------|------|
| 每个 Phase 独立 API 调用 | 2B 只能单线程，共享上下文会崩溃 |
| ID 由系统分配不由模型生成 | 模型生成的 ID 不稳定（输出过数字 1234） |
| JS 不看 HTML 只看契约 | 模型看到 HTML 就输出 HTML（实验证明） |
| 确定性验证器兜底 | 模型输出不可控，系统修复100%可靠 |
| 交互设计作为 Phase 0 | 一切从"用户做什么"出发，不从"写什么文件"出发 |

## 四、已验证的实验数据

### 2B 认知极限

| 能力 | 单独 | 组合 |
|------|------|------|
| 循环（read→advance） | 100% | — |
| 判断（是否顶级函数） | 0%（6种prompt全败） | 组合后33% |
| 认知展开（拆成微问题） | 100% | — |
| 系统编排（模型只导航） | — | **100% (6/6)** |

### 关键实验

1. **直接判断 vs 认知展开**:
   - 直接问"哪些是顶级函数" → 0%（6种 prompt）
   - 拆成子问题（"以 def 开头吗？""函数名是？"） → 100%

2. **系统编排**（`test_system_orchestrated.py`）:
   - 模型只做 read→advance 循环
   - 系统做 `line.startswith("def ")` 判断 + 隔离微对话提取名字
   - 6 个 seed 全部 F1=1.00

3. **代码开发管线**（`test_abstract.py`）:
   - 从一句话自动生成 3 个文��
   - ID 通过契约系统一致
   - JS 输出 HTML 问题由验证器兜底修复

## 五、2B 模型的已知限制及绕过方法

| 限制 | 现象 | 绕过 |
|------|------|------|
| 看不到前导空格 | backtick中`    def foo` 首字符说是'd' | 系统做 `startswith()` |
| 数空格不准 | 8空格数成10 | 系统做 `len()-len(lstrip())` |
| 多任务崩溃 | 循环+记录 → 只循环不记录 | 隔离上下文，一次一件事 |
| 输出 HTML 而非 JS | 要求纯JS但输出完整网页 | 验证器提取 `<script>` 内容 |
| 名称拆分 | `process_batch` 提取成 `process` | 模板法："格式是def NAME(...)，NAME是？" |
| JSON 不稳定 | 无引号 `[foo, bar]` | 正则提取 + 兜底默认值 |
| ID 生成不稳定 | 输出数字而非语义ID | **系统分配ID，不让模型生成** |

**总原则**: 模型做不到 100% 的事 → 程序化为确定性操作。模型只做程序做不了的（语义理解、内容生成）。

## 六、知识库拆解方法

Guild/Skills 中的知识是给人类或大模型看的，2B 看不懂。必须拆解为原子操作。

### 拆解模板

```
原始原则: [来自 Guild/Skills 的一段知识]

触发条件（确定性，代码检测）:
  [什么情况下需要应用这条——正则/关键词/AST检查]

步骤序列:
  步骤1（系统|模型）: [做什么]
    输入: [看到什么]
    输出: [产出什么]

每步约束:
  - 系统步骤: 纯代码，100%正确
  - 模型步骤: 一个简单问题，YES/NO 或一个词
  - 绝不让模型同时考虑两件事
```

### 示例：拆解"防溢出原则"

```
原始: "flex子元素可撑破容器 → 加 min-width:0; overflow:hidden"

触发条件（系统检测）:
  CSS 中存在 flex:1 且同选择器无 min-width

步骤:
  步骤1（系统）: 正则找所有 flex:1 的选择器
  步骤2（系统）: 检查是否有 min-width
  步骤3（系统）: 没有 → 自动添加 min-width:0; overflow:hidden;
  
模型参与: 无（全确定性）
```

### 示例：拆解"最少决定原则"

```
原始: "每次要求用户做决定都是消耗，用合并/默认/延迟压缩"

触发条件: Phase 0 交互设计完成后

步骤:
  步骤1（系统）: 数交互列表中需要用户"输入/选择"的步骤数
  步骤2（模型，隔离）: "这个输入必须在操作时填吗？能之后改吗？"
  步骤3（系统）: 答"之后" → 从创建流程移到属性面板
  步骤4（模型，隔离）: "这个字段最常见的值是什么？"
  步骤5（系统）: 设为默认值
```

## 九、核心哲学（一段话版）

2B 模型是单线程白痴。你给它一件简单的事，它做得完美（100%）。你给它两件事，它就崩。所以系统的工作是：把任何复杂任务拆成一串简单问题，每个问题独立问模型，问题之间的衔接全部由确定性代码处理。模型不需要记住上下文，不需要同时思考多件事，不需要做字符串操作——这些全是系统的事。模型唯一的价值是**语义理解**：知道用户想要什么、知道函数名是什么、知道交互应该怎么设计。其余一切，代码来做���
